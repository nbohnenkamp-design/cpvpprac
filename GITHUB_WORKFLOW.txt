CPVPSingleBiome – GitHub Workflow

Projektverzeichnis

cd ~/IdeaProjects/cpvpprac-stable-work

---

Build prüfen

Vor jedem Commit sicherstellen, dass das Plugin erfolgreich baut:

mvn clean package

Die fertige JAR befindet sich anschließend in:

target/CPVPSingleBiome-<version>.jar

---

Git Status prüfen

git status

Prüfen, welche Dateien geändert wurden.

---

Änderungen übernehmen

git add .

Alternativ nur einzelne Dateien:

git add src/main/java/...
git add src/main/resources/...

---

Commit erstellen

git commit -m "Kurze Beschreibung der Änderung"

Beispiele:

Improve snow spruce generation
Add end biome reset support
Fix Paper dimension reset handling
Improve Multiverse reset handling
Update README

---

Nach GitHub hochladen

git push

Falls GitHub einen neueren Stand hat:

git pull --rebase origin main
git push

---

Neue stabile Version veröffentlichen

Nur verwenden, wenn eine neue öffentliche Version veröffentlicht werden soll.

---

Versionsnummer erhöhen

Dateien anpassen:

xed pom.xml
xed src/main/resources/plugin.yml

Beispiel:

1.2.12 -> 1.2.13

---

Build erstellen

mvn clean package

---

Änderungen committen

git add .

git commit -m "Release v1.2.13"

---

Tag erstellen

git tag v1.2.13

---

Nach GitHub hochladen

git push
git push origin v1.2.13

---

GitHub Release erstellen

1. GitHub öffnen
2. Releases öffnen
3. Create Release
4. Tag auswählen (z. B. v1.2.13)
5. Release Notes schreiben
6. JAR aus "target/" hochladen
7. Release veröffentlichen

---

Modrinth Release

Nur für echte Releases verwenden.

Typischer Ablauf:

1. Version auf GitHub taggen
2. JAR hochladen
3. Changelog schreiben
4. Veröffentlichung zur Prüfung einreichen

Kleine Wartungs-Commits müssen nicht zwingend als Modrinth-Version veröffentlicht werden.

---

README aktualisieren

Bei neuen Funktionen prüfen:

xed README.md

Aktualisieren wenn nötig:

- neue Biome
- neue Commands
- neue Config-Optionen
- neue Kompatibilität
- neue Screenshots

---

Wichtige Hinweise

- "target/" niemals committen
- Alte Tags niemals wiederverwenden
- Für jede veröffentlichte Version einen neuen Tag verwenden
- Vor jedem Release immer "mvn clean package" ausführen
- Vor jedem Release mindestens einen Testlauf durchführen
